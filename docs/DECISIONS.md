# Project Decisions and Assumptions

## Purpose

This record separates confirmed constraints from provisional planning defaults. Confirmed constraints are implementation boundaries. Assumptions are conservative, reversible defaults used to plan schema, screens, and tests until the business chooses differently.

## Confirmed constraints

| ID | Confirmed constraint | Implementation consequence |
| --- | --- | --- |
| D-001 | Use Laravel 12 for this environment. PHP 8.2.12 is installed; Laravel 12 supports PHP 8.2, while Laravel 13 requires PHP 8.3. | Scaffold with a `^12.0` framework constraint and do not adopt Laravel 13 until the local and production PHP versions are upgraded deliberately. |
| D-002 | Use a Laravel MVC modular monolith with Blade, Bootstrap 5, and limited vanilla JavaScript. | Do not introduce React, Vue, Angular, Inertia, or a separate API frontend without a new decision. |
| D-003 | Use MySQL-compatible storage with InnoDB, `utf8mb4`, foreign keys, transactions, and indexed relationship/filter fields. | The local XAMPP service is MariaDB 10.4.32 and is compatible with Laravel 12's supported MariaDB baseline. Production database compatibility must be rechecked before deployment. |
| D-004 | Target standard cPanel shared hosting. | Prebuild frontend assets; production must not require a Node.js runtime, Redis, Horizon, Supervisor, a WebSocket server, or a persistent queue worker. |
| D-005 | The primary workflow is manager-driven. One Administrator/Business Manager may complete the entire Event lifecycle. | No core step may require assignment or approval by a second user. RBAC still supports later separation of duties. |
| D-006 | Booking is optional and must never be a prerequisite for Event creation or completion. | Booking references are nullable and both direct-Event and Booking-first flows require tests. |
| D-007 | Client, Vendor, and Staff are business records independent of login identities. | Their `user_id` links are nullable. Creating a domain record must not create a User automatically. |
| D-008 | Event Templates suggest modules but never force them. Module enablement is stored per Event. | Template application initializes editable selections. Disabling a populated module preserves its records and requires confirmation. |
| D-009 | Payments are entered manually in the initial release; online gateways are future scope. | Keep a provider-independent payment ledger and no gateway settings, webhook handling, card processing, or automatic bKash/bank collection in the first release. |
| D-010 | Initial outbound integrations run synchronously when enabled. | Provider errors require user feedback and logs; architecture may expose service boundaries without requiring queue infrastructure. |
| D-011 | Notifications are stored, static in-application items. | Core acceptance uses page request/refresh and optional scheduled checks, with no socket-based real-time dependency. |
| D-012 | Files use Laravel filesystem storage on the hosting account, with private access mediated by the application. | Public storage is limited to explicitly public media; documents and contracts use authorization-controlled downloads. |
| D-013 | Bootstrap runtime state uses file sessions, file cache, synchronous queues, local storage, and log mail. | The application runs on standard cPanel hosting without Redis, workers, or external providers; production credentials can be enabled later through configuration. |
| D-014 | Bootstrap 5.3.8 and its maintained Popper 2.11.8 peer are the only added frontend runtime packages. | They are compatible with the installed Vite pipeline and require no production Node.js process because assets are prebuilt. Laravel features and vanilla JavaScript remain preferred over speculative packages. |
| D-015 | The installed framework is Laravel 12.69.2 under the Composer constraint `^12.0`. | Composer resolves on PHP 8.2 and Laravel 13 remains excluded because it requires PHP 8.3. |
| D-016 | Prompt 02 exposes only the public landing page and Laravel health route. | Authentication, protected actions, list screens, workflow statuses, audit records, and domain modules remain intentionally deferred, so their Form Requests, policies, services, pagination, audit, and status-history infrastructure are not fabricated in this phase. |
| D-017 | Organize the modular monolith with normal Laravel folders and domain-oriented subfolders; do not add a third-party modular framework. | Module ownership is enforced by namespaces, service boundaries, policies, transactions, and tests while the project remains familiar to Laravel developers and simple to deploy. |
| D-018 | Use the stable module keys defined in `docs/ARCHITECTURE.md`; only the 18 event-scoped keys are stored as per-Event toggles. | Global/core modules cannot be accidentally disabled per Event. Template suggestions initialize editable Event state, dependency hints remain warnings, and disabling a populated module preserves its data. |
| D-019 | Use the database conventions in `docs/DATABASE_ROADMAP.md`: Event-centered ownership, nullable optional links, `DECIMAL(19,4)` money, UTC instants, actor/timestamp status history, and nullable `branch_id` until branch mode is enabled. | Later migrations must implement and test these invariants; Prompt 03 does not create business tables. |
| D-020 | Use native Laravel gates, policies, middleware, and explicit role/permission tables instead of adding an RBAC package. | The required authorization model is small enough for framework features; this avoids package/version risk and keeps the schema transparent. A package can be reconsidered if future requirements exceed the documented model. |
| D-021 | Public registration is disabled. Administrators create accounts; a first Administrator / Business Manager is created from local-only environment values or the interactive `app:create-administrator` command. | No production password is committed. Manager-first operation is the default while later Client, Vendor, and Staff login accounts remain optional. |
| D-022 | Users are deactivated or soft-archived rather than destructively deleted, and the final active administrator cannot be deactivated, archived, or stripped of that role. | Historical foreign keys remain meaningful, account status changes store actor/time/reason, and the installation cannot accidentally lose all administrative access. |
| D-023 | Inactive and archived users cannot log in or receive password reset links; public authentication responses do not reveal whether an account exists or is inactive. | Login attempts are recorded with an internal reason, active sessions are terminated by middleware, and externally visible errors remain generic. |
| D-024 | Build the administration shell with Bootstrap 5, custom CSS, vanilla JavaScript, and repository-owned inline SVG icons; add no icon package or general admin template. | The interface remains lightweight, works from prebuilt Vite assets on cPanel, and does not introduce a CDN, web-font dependency, SPA framework, or template-owned architecture. |
| D-025 | Reusable Blade components standardize presentation and accessibility, while authorization remains in middleware, Policies/Gates, Form Requests, and permission-scoped queries. | Hiding navigation or actions never grants security. Components use escaped output, semantic labels, visible focus, keyboard-operable Bootstrap interactions, and responsive layouts. |
| D-026 | Store the single company profile in `companies` and typed operational values in `system_settings`; encrypt secret placeholders with Laravel Crypt and never return stored secret values to forms, views, logs, or audit payloads. | Normal settings have typed access through `SettingsService` and file/database-cache-compatible caching. Empty secret fields retain the saved ciphertext, while UI and audit records expose only configured/not-configured state. |
| D-027 | Branch support uses nullable links and an explicit `BranchScope` service; no Eloquent global branch scope is installed. Branch mode remains disabled by default, administrators remain unrestricted, and null-branch legacy/current records remain visible when branch mode is later enabled. | Single-company operation cannot silently lose data. Later branch-aware queries must opt into the scope and authorization tests, and branch enablement requires deliberate assignment/backfill review. |
| D-028 | Event, Vendor, Inventory, Finance, and Document categories use separate tables and models while sharing controller/service/UI conventions. Finance categories retain a domain-specific income/expense/both direction instead of a generic metadata field. | Configurable master data can evolve with domain constraints without forcing unrelated fields or JSON metadata into one generic lookup table. Stable slugs, archive behavior, policies, filters, and audit rules remain consistent. |
| D-029 | Audit, login, generic status history, and document-version rows are append-only to normal application code; metadata passes through centralized recursive redaction before storage. | Passwords, tokens, secrets, authorization data, payment credentials, and sensitive dietary/bank values are not retained in audit JSON. There are no normal edit/delete routes. Any future retention purge requires a separate privileged, evidenced design. |
| D-030 | Protected documents use the Laravel private local disk, UUID paths, MIME/extension/size allowlists, SHA-256 metadata, immutable versions, allowlisted contextual links, and authorized streamed downloads. | Original names never determine storage paths or public URLs. Company, Branch, User, Client, Vendor, StaffProfile, Event, and Booking links are enabled explicitly by their owning prompts. Expiry alerts and a scanner-provider integration remain later scope. |
| D-031 | Client identity supports individual and organization records independently of authentication. Contact channels are normalized for search and duplicate warnings, not enforced as unique business identifiers. | Shared household/organization email addresses and phone numbers remain valid. Potential duplicates are saved with a visible warning and may be merged only through a privileged, audited operation. |
| D-032 | Client records are never destructively deleted through normal application routes. Archive/reactivate and merge preserve the master row, contacts, status history, document links, and audit evidence; portal `user_id` linkage is nullable and separately privileged. | Events, Bookings, Invoices, and Payments can safely retain restrictive Client foreign keys. Creating a Client never creates a login, and a later link/unlink action is explicitly authorized and audited. |
| D-033 | Vendor and Staff business masters are independent of authentication. Their nullable unique `user_id` may be linked or unlinked only through privileged, audited actions to an active matching-role User. | Managers can maintain complete supplier/workforce records without portal accounts. Deactivating a User never deletes or archives the business record or its historical relationships. |
| D-034 | Vendor Categories and Staff Departments are separate configurable lookup tables. Vendor/Staff archive/reactivate preserves the master row, child records, protected document links, audit evidence, and actor/timestamp status history. | Domain constraints can evolve independently. There are no destructive master delete routes, and later Event assignments reference the retained global masters. |
| D-035 | The module registry materializes all 29 stable SRS keys in `module_definitions`; only labels, display order, and active availability are editable. The unique string key, scope, and event-scoped classification are immutable application contracts. | Templates and future Events can store stable references while administrators configure presentation. Unknown or global keys fail validation, and deactivation never invalidates historical data. |
| D-036 | Applying an Event Template is a copy-on-create operation. Default recommendations, manager overrides, starter tasks, service notes, and budget suggestions produce an Event-owned snapshot; optional recommendations remain disabled suggestions and dependency relationships produce warnings only. | Template edits never rewrite existing Events. Custom Event has no preset, all specialized modules may remain disabled, and Prompt 11 will persist the snapshot with the Event transaction. |
| D-037 | The Event lifecycle is Draft to Confirmed to Planning to In Progress to Completed, with cancellation permitted from every non-terminal state. A completed Event is read-only and only events.correct may reopen it to Planning with a required reason. | Every transition is explicit, transactional, policy-protected, and appends actor/time/reason status history, timeline, and audit records. The Administrator / Business Manager may perform the entire lifecycle alone. |
| D-038 | Event instants are entered in the Event time zone, converted to UTC by the application, and stored as DATETIME(6); list/detail output uses the organization time zone and may additionally show Event-local time. | UTC remains independent of database/session time zones. DATETIME(6) avoids legacy XAMPP/MariaDB multiple-TIMESTAMP default behavior while retaining microsecond precision. |
| D-039 | Event duplication creates a new independent Draft with a new reference and null booking_id. It copies planning fields, the immutable template snapshot, every module state, and only notes explicitly marked copyable when requested. | Payments, invoices, attendance, ticket scans, prior status/timeline/audit history, completion/cancellation/archive state, and other transactional records are never copied. |
| D-040 | Every Event-scoped route must combine Event visibility, module-specific permission, and `event.module.enabled` middleware. Disabling detected module data requires separate explicit confirmation plus a reason, appends immutable change history, and never removes records. | Workspace navigation cannot be treated as security. Managers are redirected to module administration when disabled; other direct requests fail without exposing preserved data. Each later module must register a bounded data detector before storing Event-owned records. |
| D-041 | Dashboard Event KPIs are live projections over the same permission- and branch-scoped query rules used by the Event list; no duplicate KPI totals are stored. | Total, upcoming, ongoing, completed, and cancelled counts reconcile with linked filtered lists. Task and finance widgets are absent until their source modules and permissions exist. |
| D-042 | Global search is a bounded provider registry. A provider must prove permission before issuing its entity query, apply the entity visibility scope, return no hidden counts, and limit results. | Bookings, Events, Clients, Vendors, and Users are searchable now. Invoice providers may register only when that module, its policies, routes, and indexes exist. Wildcard-only broad terms are neutralized and Blade output stays escaped. |
| D-043 | Booking is an optional upstream aggregate with Enquiry, Under Review, Confirmed, Waitlisted, Converted, and Cancelled states. Approval and confirmation are one manager action by default; conversion locks the Booking, creates exactly one Draft Event, and links both rows atomically. | Direct Events retain null booking_id; repeated conversion returns the linked Event. Reschedule conflicts come from a replaceable adapter and require a separately authorized explicit override. Cancellation preserves the Booking and records finance-review flags from a replaceable adapter without deleting financial data. |
| D-044 | Venue availability is a live projection of Event schedule plus active EventVenueAllocation rows. Availability uses half-open intervals (`existing start < requested end` and `existing end > requested start`), parent Venue/Space locks inside the write transaction, and space-aware exclusive collision rules. | Adjacent allocations are valid; cancelled Events/allocations do not reserve time. Capacity is advisory and currently compares expected guests with the selected space or Venue capacity. Conflict override requires `venues.override-conflicts`, a reason, actor/time history, and an audit entry. Venues may be owned or third-party; optional rate rows never replace per-Event quoted price. |

| D-045 | Vendor commitments use half-open schedule overlap checks under a locked Vendor parent. The default conflict policy is warn; administrators may configure block, and explicit unavailable windows independently select warn/block behavior. Approved assignment cost is the vendor-cost source exposed through ApprovedVendorCostProvider; vendor invoice uploads are protected metadata and do not create Expenses or Payments. | Adjacent commitments remain valid. Conflicts are visible and audited without a hidden override path, archived Vendors cannot receive new assignments, and future Finance code must consume the provider contract or define an explicit idempotent posting rule before creating an Expense. This default is reversible through Vendor configuration. |
| D-046 | Staff availability is derived from active half-open Shift/Event-assignment windows plus approved Leave under a locked Staff parent. Conflicts block unless the staff.override-conflicts permission supplies a reason. SalaryRecord is a permission-isolated operational salary/payment tracker, not statutory payroll. | Adjacent work remains valid; approved leave affects availability; overrides retain actor/reason/conflict evidence; archived Staff history survives. Taxes, deductions, benefits, payslips, and filings remain outside this module under reversible default A-004. |
| D-047 | Event Tasks are optional, assignment-aware records with dedicated append-only status history and protected Document attachments. Overdue state is derived from deadline/completion. Calendar is a bounded permission/branch/time-zone projection of existing Events, Venue allocations, Staff schedules, Vendor assignments, and Task deadlines; it owns no generic schedule table. | Task disablement hides normal routes and Calendar deadlines while preserving records. Linked Staff sees only assigned tasks. Schedule changes appear immediately without synchronization, queue workers, Redis, or duplicate calendar data. |
| D-048 | Event budgets are planning records separate from actual income and expense ledgers. Recognized income/expense is the algebraic sum of posted entries, including posted reversals; Draft and Void entries do not affect profit. Posted originals are immutable and a correction creates a linked equal reversal rather than changing or deleting the original. | `FinanceService` is the authoritative posting, reversal, actual-versus-budget, and profit boundary. `DECIMAL(19,4)` and string decimal arithmetic prevent floating-point money calculations; source type/ID uniqueness prevents the same operational cost or income from being counted twice. |
| D-049 | Manual client Payments are immutable positive receipt entries. Posting creates one explicitly linked posted Income through FinanceService; Refunds are immutable positive records represented in recognized Income as posted reversal entries. Payment schedules remain optional due plans, while an Invoice is the payable obligation when present; corrections use Refund plus replacement rather than editing history. | Payment, allocation, Refund, Income, status, and audit writes share one transaction with parent/target locks and idempotency keys. Prompt 21 adds restrictive foreign keys to every nullable Invoice extension column and reconciles Invoice balances without changing the Payment source of truth. No gateway, webhook, checkout, card, payment-method settings, or provider adapter exists. |
| D-050 | An issued Invoice is an immutable financial snapshot. A locked prefix/year sequence assigns its number; stored line values calculate discount before tax with deterministic four-decimal half-up arithmetic; Payments reconcile status and balance through allocations; cancellation or a linked credit note preserves the original. | Drafts alone are editable. Overdue is derived, PDF/print/email render stored totals, email remains synchronous with immutable delivery attempts, and Invoice issuance creates no duplicate Income. Restrictive foreign keys now protect every Prompt 20 Invoice reference. `barryvdh/laravel-dompdf` 3.1.x is the only added PDF dependency and remote/PHP rendering is disabled. |
| D-051 | In-app notifications are stored and static. Role targets are resolved to active users at creation so read state is private per recipient; record links store only allowlisted Laravel route names and parameters. Outbound communication is a synchronous, append-only attempt log: email uses Laravel mail, while SMS and WhatsApp are explicit unavailable adapters until separately configured. | No browser push, WebSocket, Redis, queue worker, arbitrary notification URL, or provider SDK is required. Operational and marketing messages retain separate consent bases; marketing sends require explicit consent confirmation. Failures store only sanitized codes and may be retried without overwriting prior attempts. This preserves reversible defaults A-007/A-008. |
| D-052 | Guest check-in uses a 256-bit opaque base64url token per Invitation: only its SHA-256 hash is indexed, while an encrypted copy supports authorized QR re-rendering. QR output contains the check-in URL and token only. `endroid/qr-code` 6.0.9 under `^6.0` is the documented SVG renderer after Composer verification for PHP 8.2. | Tokens are non-guessable and no Guest personal data is embedded in QR content. Invitation/check-in operations remain synchronous; Event-constrained lookup, row locking, an append-only unique check-in row, authorization, expiry/revocation checks, and audit provide safe one-time attendance without an external QR service. |
| D-053 | Registration is an Event-owned optional module independent of Ticketing. Form definitions use only allow-listed field types and structured constraints; submissions snapshot every response; public access uses a random slug, CSRF, throttling, and a replaceable spam guard; review history is append-only. | Form edits never rewrite earlier answers. Approval confirmation uses the existing synchronous communication boundary, explicit Guest conversion is idempotent and separately authorized, and disabling Registration hides access while preserving all forms, submissions, responses, and history. No package was added. |
| D-054 | Ticketing is Event-owned, quantity-based general admission. Ticket Type capacity is guarded by a transaction and parent-row lock; every Ticket stores immutable price/discount/currency snapshots and a 256-bit opaque credential as SHA-256 lookup hash plus encrypted render copy. QR rendering reuses the already verified local `endroid/qr-code` 6.x dependency. | No seat map, hold daemon, online checkout, gateway, card data, or external QR provider is introduced. An Event must be explicitly published and Ticketing enabled before any public catalogue, Ticket page, or QR is exposed. Front-desk validation is Event-isolated and append-only; repeat scans return the original actor/time. |
| D-055 | A priced Ticket Order must reference sufficient unallocated value from a posted manual Payment. Ticket refunds preserve the Ticket and order, invalidate admission, and call PaymentService for a traceable manual Refund/Income reversal; free Tickets create a zero-value TicketRefund without fabricating a financial or gateway transaction. | Ticketing does not duplicate Income/Expense totals and does not claim a gateway refund. Cancellation cannot bypass a required paid refund, and used Tickets cannot be refunded or cancelled. Released refunded/cancelled quantity returns to general-admission availability. |

## Assumptions and reversible defaults

Every item in this section is reversible. Reversal may require migrations, UI changes, new integrations, additional tests, or revised estimates, but the design should avoid destructive rewrites.

| ID | Reversible default | Material scope effect | Reversal path or trigger |
| --- | --- | --- | --- |
| A-001 | Single company. | Material if the product must serve multiple independent companies or tenants. | Add tenant ownership, tenant-scoped uniqueness, isolation policies, onboarding, and tenant administration before production data is loaded. |
| A-002 | Branch columns and relationships exist where relevant, but branch features and branch-scoped permissions are disabled by default. | Material if several branches need operational isolation at launch. | Enable a feature/configuration flag, require branch assignment, expose branch administration, and run the prepared branch-isolation tests. |
| A-003 | Booking approval uses one manager action. | Material if multi-level or department approvals are required. | Introduce configurable approval stages, approver rules, escalation, and stage history without changing the optional Booking-to-Event relationship. |
| A-004 | Staff salary is simple salary/payment tracking, not statutory payroll. | Material if tax, deductions, benefits, payslips, or jurisdictional filings are required. | Replace or integrate the ledger with a separately specified payroll module/provider and add compliance tests. |
| A-005 | Tickets are quantity-based general admission; assigned seats are out of scope. | Material for reserved seating, numbered sections, or seat maps. | Add Venue seating inventory, seat holds, allocation timeouts, and seat-specific ticket validation. |
| A-006 | Marketing supports planning, audience, consent, coupons/referrals, content/link tracking, and metrics without direct publishing to social networks. | Material if staff expect the system to publish posts. | Add separately authorized provider adapters, account/token management, platform review, scheduling semantics, and provider-specific tests. |
| A-007 | Browser push is not implemented. Static in-app notifications remain in scope. | Material only if alerts must appear while the application is closed. | Add opt-in, service worker, subscription storage, provider selection, browser support policy, and delivery/privacy tests. |
| A-008 | Email, SMS, WhatsApp, maps, and other communication providers are disabled until valid credentials and sender configuration exist. | Usually operational rather than business-scope material, but launch communications may depend on it. | Enable channels individually after credentials, consent/template rules, failure handling, and a production send test are approved. |
| A-009 | Invoice prefix, sequence, tax rate/rules, and rounding are configurable; no jurisdiction-specific legal format is assumed. | Material if invoices must meet a statutory format or fiscal-device rule. | Configure agreed values or add a jurisdiction-specific invoice profile and legal acceptance tests. |
| A-010 | Files use local protected Laravel storage on the hosting account. | Material if expected volume, disaster recovery, or distribution requires object storage/CDN. | Switch the filesystem disk through the storage abstraction, migrate objects, and re-run authorization/backup tests. |
| A-011 | A Client may be omitted only while an Event is Draft; a Client is required before any transition out of Draft. | Material for internal, demo, or non-commercial Events that must progress without a Client. | Add an explicitly authorized internal-event type or relax the transition rule with corresponding reporting and finance behavior. |
| A-012 | Every Event module is optional except the core Client to Event flow and cross-cutting security/audit behavior. | Material if any operational module must be mandatory for a category or company policy. | Add configurable required-module rules at company/category level while retaining Event overrides only where allowed. |
| A-013 | The application timezone defaults to UTC until the authoritative business timezone is confirmed. | Operationally material for schedules and reports, but it does not change feature scope. | Set `APP_TIMEZONE` before real business data is entered, document the chosen zone, and test date-boundary reports and schedules. |
| A-014 | Approving an Event budget locks its planning lines as the current baseline; versioned budget revisions are not included yet. | Material only when managers must revise an already approved baseline while retaining multiple approved versions. | Add explicit revision records and a reasoned supersede workflow that preserves every prior approved baseline and recalculates comparisons against the selected revision. |
| A-015 | A manual overpayment remains an unallocated client advance/credit; due is floored at zero. Allocated refunds reopen the selected obligation, while unallocated refunds may consume only unallocated credit. | Material if the business requires automatic oldest-due allocation, unrestricted cross-allocation, or a separate client wallet. | Add a confirmed allocation policy and migration/service changes while preserving every original Payment, allocation, and Refund row. |
| A-016 | Invoice line discounts are applied before tax; values round half-up to four decimal places; sequence year is the issue year; issuing an Invoice does not itself recognize Income. | Material if the applicable jurisdiction or accounting policy uses tax-inclusive pricing, invoice-level rounding, another tax/discount order, fiscal numbering, or accrual recognition at issue. | Add a versioned jurisdiction/accounting profile and migrate only future Draft calculations while retaining every issued snapshot and credit trail. |
| A-017 | Guest invitations allow one active token per Guest; check-in is one-time per Guest with an admitted party size; seating uses free-text table/seat labels; Venue capacity excess is a warning. This default is reversible. | Material if Invitations need multiple simultaneously valid credentials, attendee-level scans inside a party, graphical reserved seating, or a hard capacity block. | Add versioned Invitation/attendee credentials, per-person attendance rows, a Venue seat inventory/hold model, or configurable capacity enforcement while retaining existing Guest and check-in history. |
| A-018 | Registration forms require manager approval by default and block a second non-rejected submission with the same normalized email. Confirmation defaults to none; enabling email/SMS requires an enabled Communications module and a usable adapter. This default is reversible. | Material if an Event permits multiple registrations per email, needs automatic approval, or requires launch-day confirmations. | Change the per-form duplicate/approval/confirmation configuration; existing submissions and response snapshots remain intact. Configure and verify the selected communication adapter before production use. |
| A-019 | Promo percentage or fixed discounts apply per Ticket; usage limits count issued Ticket quantity and are not restored by later cancellation/refund. Public Ticket links are available only while the Event catalogue is explicitly published. This default is reversible. | Material if fixed discounts should apply once per order, redemptions should be restored, or Ticket links must remain usable after catalogue unpublication. | Version the Promo rule/snapshot semantics for future orders and add a separate credential-publication policy; never recalculate existing issued Ticket snapshots. |

## Open details that remain unconfirmed

These items are intentionally not converted into hidden business decisions:

- Refund and cancellation formulas for Bookings.
- Launch languages, currencies, and the authoritative business timezone.
- Expected users, Events per year, attendees/tickets per Event, and storage volume.
- First-release Client, Vendor, or Staff portal screens, if any.
- Initial Event Categories/Templates and their suggested module sets.
- Data retention periods, backup retention, recovery point objective, and recovery time objective.
- Reports requiring legal/statutory formatting rather than management-only output.
- cPanel cron availability and production PHP/database versions.

## Change control

When an assumption changes, record the replacement decision here, update the affected traceability rows, assess existing data migration, and revise tests before implementation. A default becoming confirmed should move from the assumptions section to the confirmed constraints section with the confirming date and source.
